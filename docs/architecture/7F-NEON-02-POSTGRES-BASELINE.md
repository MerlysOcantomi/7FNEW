# 7F — NEON-02 — PostgreSQL canonical baseline (Phase 1)

Status: prerequisite satisfied (FOUND-04A-SCHEMA on `master`, commit
`d1c14f5`), baseline `0_init` generated from the canonical schema and verified
from zero locally (see §3, §5). Nothing here changes the Turso runtime, the
canonical schema provider, `core/db.ts`, the SQLite history or production.

## 1. Decisions this design implements

- **D1** PostgreSQL gets a NEW history; the SQLite migrations `0..6` are never
  translated one by one.
- **D2** One canonical `0_init`, generated from the target canonical schema
  (`prisma migrate diff --from-empty --to-schema … --script`).
- **D3** FOUND-04A's provider-neutral schema state (`Workspace.entitlementRevision`,
  model `WorkspaceEntitlement`, its FK and unique) belongs in the baseline; the
  Turso applier (`scripts/apply-found04a-migration.ts`) does not.
- **D4/D6** Fidelity, not redesign: no Decimal, no JSONB, no enums, no UUID, no
  identity sequences. Types map to `TEXT`, `TIMESTAMP(3)`, `BOOLEAN`,
  `DOUBLE PRECISION`, `INTEGER` only.

## 2. Layout — one canonical source, one derived variant, one generated history

| Path | Role | Tracked |
|---|---|---|
| `prisma/schema.prisma` | canonical schema (SQLite provider while Turso is the runtime) | yes |
| `generated/schema.postgres.prisma` | **derived** variant: only `provider = "postgresql"` and the client `output` path differ; regenerated by tooling, never hand-edited | no (`generated/` is gitignored) |
| `prisma/migrations-postgres/0_init/migration.sql` | the PostgreSQL baseline, empty → variant | yes (once generated from the prerequisite state) |
| `prisma/migrations-postgres/migration_lock.toml` | `provider = "postgresql"` | yes |
| `prisma.config.postgres.ts` | Prisma config used only with `--config`; schema = variant, migrations = `migrations-postgres`, url = `POSTGRES_DIRECT_URL` (no dotenv) | yes |
| `scripts/postgres-baseline.ts` | `generate-schema`, `generate-init`, `verify` | yes |

The SQLite history and the PostgreSQL history never share a directory. Prisma
7.4.1 does **not** refuse a cross-provider `migrate diff` (it silently emits
`DROP TABLE` × N + `CREATE TABLE` × N), so provider separation is enforced by
the config file and the tooling, not by the CLI.

```
npm run db:postgres:schema   # generated/schema.postgres.prisma  (derivation, prints sha256)
npm run db:postgres:init     # prisma/migrations-postgres/0_init  (refuses to change an existing baseline)
npm run db:postgres:verify   # needs POSTGRES_DIRECT_URL → an EMPTY, ephemeral, loopback PostgreSQL
```

`generate-init` is immutable by construction: it writes `0_init` only when the
file does not exist, reports an identical file as unchanged, and hard-fails on
any difference. There is no override flag — schema changes after publication go
into a NEW PostgreSQL migration. (Restarting the history is a deliberate owner
act on a private, unmerged branch: delete the directory by hand; the tracked
tooling never offers it.)

`verify` proves, in order (R3): (1) the variant on disk equals a fresh
derivation; (2) `0_init` exists and passes the static audit (no `PRAGMA`,
`DATETIME`, `AUTOINCREMENT`, `rowid`, `sqlite_*`, table rebuilds, `?`
placeholders, SQLite functions; no `SERIAL`/identity, `JSONB`, enums, UUID,
`DEFERRABLE`, extensions, `TIMESTAMPTZ`, `NUMERIC`; no identifier over 63
characters); (3) **preflight, before any DDL**: the target database is EMPTY —
a read-only `DO` block over `information_schema.tables` (every base table
outside the system schemas counts, `_prisma_migrations` included) executed
through `prisma db execute`, plus `migrate diff --from-empty
--to-config-datasource` must be empty; any user table fails the run with
"requires an EMPTY disposable database" and nothing is applied; (4) the first
`migrate deploy` must apply `0_init` **in this invocation** ("No pending
migrations" is rejected); (5) the ledger holds exactly one row, `0_init`,
`applied_steps_count = 1`, `finished_at` non-null, `rolled_back_at` null
(read-only `DO` block); (6) `migrate diff` applied-DB → variant is empty;
(7) a second `migrate deploy` is a no-op.

It refuses any non-loopback host unless `POSTGRES_VERIFY_ALLOW_REMOTE=1` is set
explicitly. That override bypasses **only** the hostname restriction: the
empty-database preflight, the ledger requirements and the baseline immutability
apply identically. It exists for a disposable non-production database, never
for Neon production. Connection URLs are never printed.

## 4. NEON-01 on PostgreSQL (rehearsed with `pg` + `@prisma/adapter-pg`, local only)

- attention-count and unanswered raw SQL: `$1…$n` placeholders, quoted mixed-case
  identifiers, `"isInternal" = FALSE`, `Date` threshold binding — same results as
  the SQLite equivalence fixture (assigned 4, lead 1, unanswered sets).
- `COUNT(*)` arrives as `bigint` through the Prisma adapter (string through raw
  `pg`); `countFromRows` coerces both.
- Free-text search: plain `contains` is case-sensitive on PostgreSQL;
  `mode: "insensitive"` restores today's behaviour → to be added in
  `core/db-search.ts` (`searchContains`/`searchStartsWith`) at the provider flip.
- RFC Message-ID lookups (In-Reply-To, References, duplicate): plain `contains`
  MISSES the mixed-case persisted id; `mode: "insensitive"` finds it → those four
  lookups in `modules/inbox/email-inbound.ts` must gain `mode: "insensitive"` at
  the flip. The historical `sourceId` fallback matches verbatim without change.
- Structured filters (`structuredContains`): case-sensitive on PostgreSQL; the
  semantics decision stays open (no evidence of a case-insensitive contract).

## 5. Prerequisite — satisfied

The target baseline requires FOUND-04A's schema state. The derived-variant
mechanism deliberately rewrites only the provider line: baking the FOUND-04A
model into a generated file from anywhere but `prisma/schema.prisma` would
have created a second, divergent canonical schema.

That state now lives on `master` (FOUND-04A-SCHEMA, commit `d1c14f5`): the
`prisma/schema.prisma` delta, the reviewed SQLite migration
`6_found04a_workspace_entitlements` (sha256 `44e6b04f…`; `db:verify-history`
at 50 tables / 94 indexes, drift 51 = manifest 51) and the verifier
constants — WITHOUT the runtime readers and WITHOUT the Turso applier.
Production Turso simply reports migration 6 as pending, which is harmless
because nothing on `master` reads the table.

Acceptance check, met: `npm run db:postgres:schema && npm run db:postgres:init`
on `master` `d1c14f5` reproduces `prisma/migrations-postgres/0_init/migration.sql`
with sha256 `679d9d18e72a3fa101bd96f6c39b2194ba38ae86de35359a3e46be8d662af30e`,
byte for byte the file rehearsed in §3 — with no overlay and no second source.
`generated/schema.postgres.prisma` stays gitignored: it is a pure derivation,
regenerated by the tooling and by CI, so committing it would only create a
copy that can go stale.

## 6. CI gate design (not applied yet)

Add a job to `.github/workflows/ci.yml` once `0_init` exists on `master`:

```yaml
  postgres-baseline:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: postgres, POSTGRES_DB: verify }
        ports: ["5432:5432"]
        options: --health-cmd "pg_isready -U postgres" --health-interval 5s --health-timeout 5s --health-retries 10
    env:
      DOTENV_CONFIG_PATH: /dev/null
      POSTGRES_DIRECT_URL: postgresql://postgres:postgres@localhost:5432/verify
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run db:postgres:schema
      - run: npm run db:postgres:verify
```

No external credentials: the service container is ephemeral and loopback-only,
which keeps the existing "CI needs nothing from the environment" property.
